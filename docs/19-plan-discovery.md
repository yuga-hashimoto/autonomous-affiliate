# 19. 計画の自動発見（公式の一覧ページ → 計画）

計画（`ArticlePlan`）を手で書き足す運用は、最後の1件を公開した日に止まる（docs/16「公開の上限と残り」）。計画の概要は、公式ページが一覧に出している「サービスの名前」から機械的に作れる。金額は docs/18 の仕組みが引用から決めるので、ここで作るのは**概要だけ**である。

## 範囲

- 水（ボトル型ウォーターサーバー）の機種だけ。docs/18 の `draft` が水だけだから。
- 発見元（`config/discovery.live.json`）は本人・AIが決める: 一覧ページのURL、会社名、プラン名、比較の前提（`months`、`monthlyLiters`）。**会社を足すには許可ドメインへの追加（本人の規約確認、ADR-011）が先に要る。** 許可外の発見元は1回もアクセスせずに読み飛ばす。
- 手書きの計画（`LIVE_PLANS_JSON`）は何も変わらない。同じ `slug` の発見分は捨て、手書きが勝つ。

```json
{
  "sources": [
    {
      "verticalId": "water_delivery",
      "brandSlug": "premium-water",
      "brandName": "プレミアムウォーター",
      "planName": "もっとPREMIUM",
      "listUrls": ["https://premium-water.net/price/motto/"],
      "sourceUrls": ["https://premium-water.net/price/motto/", "https://premium-water.net/price/"],
      "months": 24,
      "monthlyLiters": 25
    }
  ]
}
```

## 流れ（`discoverPlans`、毎回の `live-pipeline` の最初）

1. 発見元ごとに、`listUrls` と `sourceUrls` の**全て**が許可ドメインにあることを確かめる（`splitByAllowlist`）。1つでも外なら取得せず `domain_not_allowlisted` として数える。
2. 一覧ページを取得し、可視テキストを窓に分けて、LLM（`PlanLister`）に「商品そのものの名前」を挙げさせる。渡すのは会社名とページ本文だけ。
3. コードが名前を検査する（`findServiceNames`）。**ページの行そのもの**であり、その行が**2回以上**現れること。会社名・プラン名を含むものは除く。括弧の注記・空白・ゼロ幅空白の違いは同じ機種とみなす。LLMの並びではなく**ページの出現順**に並べる。ページに無い名前（作った名前）は捨てる。
4. 名前から計画を作る（`planForService`）。`slug` は会社・名前・期間だけから決める（`premium-water-famfit2-24month`。日本語を含む名前は固定のダイジェストを付ける）。LLMの言い回しが変わっても、同じ機種は毎日同じ計画になる。計画は `draft` だけで金額を持たない。
5. 手書きの計画と合わせて `runPlanQueue` に渡す。新規は1日の上限まで、公開済みの更新は毎日、金額は docs/18 が引用から決める。

発見が失敗した日（LLM障害・ページ取得不可）は、その発見元の計画が出ないだけで実行は続く。公開済み記事の更新はその日見送られ、翌日に拾われる。

## 守っていること

- 作った名前・数字は公開に届かない: 名前はページの行と照合し、金額は docs/18 の引用検査と規則を通り、QAを通らなければ公開しない。実在しない商品名を挙げても、下書きに失敗して隔離されるだけで記事にはならない。
- ログは件数だけ（`discovery: {sources, found, skipped}`）。
- 新しい記事の公開は従来どおり `new_articles_per_day` が上限。

## 限界

- 起こせない機種は、同じ実行の中で3回まで選び直したあと**隔離される**（docs/18「限界」。QUARANTINED は翌日以降は再試行されない）。実ページ（premium-water.net のもっとPREMIUMプラン）では、機種5つのうち famfit2 は手書きの計画で公開済み、amadanaスタンダードは起こせると測定済み、スリムサーバー4・amadanaグランデ・AURAは規則が止まる（docs/18）。止まった機種は隔離のまま残り、規則を直しても自動では出ない。
- 1つのプランの一覧ページからは、機種の数が記事の数の上限になる。別のプラン（ずっとPREMIUM）は別の発見元として足せるが、その金額の読み取りは未測定。
- 会社を増やすには本人の規約確認が要る。人の関与なしに増やせる記事の総数は、許可済みの会社の機種数で決まる。
- 機種名の同一性は、ページ上の表記が揺れても括弧・空白を除いて同じなら同じとみなす。ページの改装で名前の書き方自体が変わると、別の機種として新しい記事が作られうる。

## 実ページでの結果（premium-water.net のもっとPREMIUMプラン、2026-10-30、CIの `live-preview`）

本番と同じAPI経路・公開なし。LLM費用 47円（6計画）。選び直しの追加前の測定。

| 機種 | 結果 |
| --- | --- |
| famfit2 | 起こせ、QA PASS（手書きの計画と同じ `slug`。公開時は手書きが勝つ） |
| amadanaスタンダード | 起こせ、QA PASS。水代4,082円・電気代1,060円・初期費用3,300円・レンタル料0円で24ヶ月 126,708円（公式ページと一致） |
| スリムサーバー4・amadanaグランデ・AURA | `plan_draft_failed`（規則が止める。docs/18の測定と同じ） |

同じ実行の手書きのプレビュー計画（金額を手で書いたもの）は、LLMが書いたFactに `36L` が出ず `plan_numbers_match_facts` でQAに落ちた。docs/18が言い換えのFactを根拠にしない理由の再現で、発見で作る計画（引用が根拠）では起きていない。

## 手書きの計画を外した（2026-10-30）

手書きの famfit2 の計画は、LLMが書き出したFactから金額の一致を確かめるため、言い換えの揺れでQAに落ちるおそれがあった（上のプレビューで再現）。`LIVE_PLANS_JSON` を `{"plans":[]}` にして、famfit2 も発見の計画（引用が根拠）に任せた。

本番で `live-pipeline` を `template_revision=discovery-1` で実行し、公開中の2本を発見の計画だけで作り直した（run 40996602626）。2本とも `updated`・QA PASS・LLM費用19円。famfit2 の数字は手書きの計画の記事と同じ（総額119,916円、水代100,560円、電気代16,056円）で、最終確認日だけが更新された。
