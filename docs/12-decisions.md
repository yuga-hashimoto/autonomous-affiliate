# 12. Architecture Decisions & Open Questions

## ADR-001: Human-free operation, fail closed

Decision: 通常運用に人間承認を置かない。例外は自動的に隔離/停止、通知のみ。人間が必要な外部法的/本人手続きは初期接続要件に分類。

Consequence: 公開量より信頼性を優先する。QA未確定ならコンテンツは公開できない。

## ADR-002: Evidence-first content

Decision: Agentの文章ではなく、公式一次情報・透明な料金式と前提・比較条件を主なソースとする。MVPでは実機検証をしない。

Consequence: 実際に使っていないサービスの体験レビューは禁止。一次情報から独自の比較・計算・判断材料を作れないなら掲載しない。

## ADR-003: Model-agnostic gateway

Decision: OpenCodeを中心候補としながら、Adapter interfaceで複数モデル/プロバイダーを接続できるようにする。

Consequence: 無料枠に依存せず料金・速度・品質の実測で切り替える。

## ADR-004: Static-first distribution

Decision: Astroの静的サイトとGit経由の公開。動的機能は必要時のみ導入。

Consequence: 低コストでバージョン/rollback追跡が容易。

## ADR-005: GitHub Actions first; durable workflow later

Decision: 小規模MVPはGitHub Actionsでスケジュール。stateをDBで保持。規模が増えたらTemporal等に移す。

Consequence: cron遅延やActionsの上限に注意。Cloudflare Pagesだけではブラウザテストを実行しない。

## ADR-006: Program access is opt-in

Decision: ASP/広告主審査が完了し、掲載・追跡・宣伝が許可されたprogramだけactive化。案件条件は実データから読み込む。

Consequence: 実案件がゼロの期間は収益リンクを持たない有益コンテンツのみ、または自動公開停止。

## 未確定（実装着手時に検証）

1. ドメイン名・正式ブランド名・商標チェック。
2. プログラム登録結果と各案件の媒体/PPC/動画/メール条件。
3. OpenCode連携の実際の非対話実行API/CLI仕様と認証・課金方式。
4. Hosting/DB/Storageの価格・無料枠・ジョブ制限。
5. 動画生成と各SNSの公式アップロードAPI・審査要件。
6. クッキー同意・プライバシーポリシー・メール配信の要件。
7. ASP attributionの粒度とレポート取得許可。
8. オープンソース化する場合のLICENSE選択（現時点では未設定）。

## ADR-007: Hands-on testing removed from MVP

MVPではSaaSの実機操作を必須としない。公式の料金・機能・制約を構造化したAnalysis Agentを採用。使用経験や実測結果を捏造しない。必要になれば後続Phaseで再判断する。

## ADR-008: Own domain and search first

記事の正本と収益リンクは独自ドメイン。検索流入を主軸にYouTube/Xを補助。noteの個人向け非公式投稿経路やQiita/Zennでの販促量産は採用しない。
## ADR-009: ユーザーはAIアフィリエイトを希望していない

Decision: AI/SaaSなど特定ジャンルを既定値とせず、国内ASP案件・検索需要・競合・実効報酬・購入障壁・法令/完全自動化適性を横断比較する。初期調査の結果に基づき専門サイトのジャンルを選定する。

Consequence: 過去のn8n/Make/AI系の記事20本は既定の公開計画ではない。AIを優先するロジックを実装に含めない。

## ADR-010: 公開済み記事は更新パスだけが置き換える

Decision: 公開済み（PUBLISHED / MEASURING / UPDATE_CANDIDATE）の記事は新規記事パイプラインから切り離し、更新パス（`runArticleUpdate`）だけが再調査・再QAして置き換える。QAに通り、サイトがビルドでき、commitできた時だけファイルを入れ替え、そうでなければ前版を残す。状態は実際に入れ替わった時だけ進める。ジョブは「トリガー+サイクル+policy_version」をkeyにして、同じトリガーの繰り返しは何もせず新しいサイクルは実行する。更新は `new_articles_per_day` を数えない。

Consequence: 失敗した更新は公開内容を変えないが、失効した価格の記事が前版のまま残り続けうる（`最終確認日` は前回のまま）。再試行は3回で止まり、計画（`LIVE_PLANS_JSON`）の修正が必要。REVOKEDは状態の変更だけでファイルの撤去はまだ自動化していない。

## ADR-011: 計画の在庫は待機させ、失敗にしない

Decision: 日次実行は計画の在庫を上から順に処理する。許可ドメインの外の計画（`domain_not_allowlisted`）と、日次上限（`new_articles_per_day`）に当たる新規計画（`daily_limit`）は**待機**とし、公式ページの取得もLLM呼び出しもジョブの記録もしない。待機は実行全体を止めない。上限の判定は公開ゲートと同じ関数（`newArticleCapReached`）を使い、公開済み記事の更新は対象外。実行結果とActionsのサマリーには理由別の件数だけを出し、計画の名前・会社は非公開のまま本人の端末の `plans-status` でだけ出す。

Consequence: 本人の規約確認（許可ドメインへの追加）は在庫の外に残り、日次運用に承認待ちキューは入らない。待機中の計画は何も記録しないため、条件が満たされた日にそのまま拾われる。許可外の計画が1件あっても公開済み記事の更新は止まらない。許可ドメインの設定ミス（打ち間違い）は「待機」に見え、サマリーの件数でしか気づけない。計画を作る部分は未実装。

## ADR-012: 計画の金額は公式ページの原文の引用から規則で決め、LLMに選ばせない

Decision: 計画は概要（`draft`）だけを持ち、円の金額は研究の直後に決める（docs/18、`draftPlanFromPages`）。LLMはページ本文から「計画に当てはまる原文の範囲」を引用するだけで、コードが引用の実在（ページ本文にそのまま在るか）を検査し、通った引用だけを決定論的な規則で読む。LLMが書いたFact（言い換え）は根拠にしない。引用が無い・曖昧・食い違うときは計画を作らず、新規は隔離、更新は前版を残す。読んだ引用は原文のままFactとして保存し、QAの数値一致検査はそれを根拠にする。

Consequence: 数字を作る・変えた引用は本文との照合で落ちる。LLMの言い回しの揺れに左右されない（言い換えのFactから読む最初の方式は、実ページで3回とも起こせなかった）。引用を選べない日は起こせずに止まる。金額が「実在する」ことは確かめるが、「記事の前提に当てはまる」ことまでは確かめられない。実ページの測定は1サイト・1計画（docs/18）。

## ADR-013: 計画は公式の一覧ページから毎日作り、手で書き足さない

Decision: 計画の在庫を手で書き足さず、許可ドメインにある公式の一覧ページ（`config/discovery.live.json`）から、毎回の `live-pipeline` の最初に作る（docs/19、`discoverPlans`）。LLMはページの行にある商品名を挙げるだけで、コードが「ページの行であり2回以上現れる」ことを検査し、ページの出現順に並べ、会社・名前・期間だけから `slug` を決める。作る計画は `draft` だけで金額を持たず、金額は ADR-012 の引用と規則が決める。手書きの計画と同じ `slug` では手書きが勝つ。許可ドメインの外の発見元は1回もアクセスしない。

Consequence: 計画を作る手作業が日常運営から消え、会社の追加（本人の規約確認と許可ドメインへの追加）だけが人の作業として残る。名前の取り違えは下書きの失敗か QA の不合格として止まり、記事にならない。止まった機種は隔離のまま再試行されない。ページの表記が大きく変わると、同じ機種が別の `slug` の記事になりうる。発見が失敗した日は、発見で作られた公開済み記事の更新が翌日に見送られる。

## ADR-014: A8の提携確認・申請・広告リンクの取得は毎日の実行の最初に自動で行い、記事は止めない

Decision: オーナーの指示（2026-10-30）に従い、`live-pipeline` の最初に `a8-sync` を実行する（docs/20）。A8に1回ログインし、設定のブランドごとに提携中の一覧・申込中の一覧を読み、未提携なら申請し、提携中なら広告リンクのページから追跡URLを読む。結果はDBに保存し、offerは「プログラムが承認済み・リンクあり・規約の確認が7日以内」の時だけ有効にする。リンクはDBの専用列に置き、型・ログ・コミットに出さない。書き出し（`export-go-offers`）は追跡URLの形に完全一致するものだけをビルド時に作る。広告主の規約は公開ページの指紋の変化とタイトル規則（QA `offer_title_rule`）で機械的に検査する。

Consequence: 提携が切れる・規約ページが変わる・リンクを読めない日は、offerが自動で無効になり、記事は収益リンクなしで公開される（記事の公開は止めない）。同名のプログラムが複数あると何も決めず申請もしない。規約ページの変化は読み直すまでリンクを止める（読み直しをLLMの判定で通さない）。広告掲載URLの登録が必要なプログラムでは、登録が済むまで成果にならない可能性が残る（未自動）。CAPTCHA・追加認証・規約同意は通過せず、再試行もしない。

## ADR-015: 新しい広告主はA8の検索から規則で選び、DBに登録して、提携が成立してから記事にする

Decision: オーナーの指示（2026-10-30）に従い、毎日の同期（`a8-sync --scout`、docs/21）が、A8の検索で水のプログラムを探し、詳細ページの規則（比較・ランキング・価格を禁じていないか）と広告主のサイトを読み、広告主のサイトの検査（robots.txt・利用規約の自動収集の禁止・提携者向けページの禁止・公式の料金ページから機種名が取れること）に通ったものだけをDB（`scouted_brands`）に登録する。登録した広告主は設定のブランドと同じに扱われ（申請・広告リンク・URL登録・規約の指紋）、提携が成立した（`active`）ものだけ、料金ページから計画を作り、そのホストを許可ドメインに加える。規則はすべてコード。LLMは料金ページの機種名の候補を挙げるだけで、ページの行との照合はコードが行う。選んだ広告主すべてに、題名の冒頭・過半に社名を使わない規則（QA）を課す。

Consequence: 許可ドメインへの追加（以前は本人の規約確認、ADR-011）が、コードの規則による確認に代わり、日常運営から人の作業が消える。見つけにくい言い回しの禁止は見逃しうるので、最後の防御は記事のQAと提携の審査に残る。使用中の広告主は3件、1回の検査は2件に絞る。商材は水に限る（下書きの経路が水だけ）。広告主の名前・サイト・プログラムIDはDBだけに置き、ログには件数と理由の種類だけを出す。`A8_SCOUT_ENABLED` を `true` にした時だけ日次の同期に含まれる（止めるには変数を外す）。
